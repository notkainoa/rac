# Council review: rac vs Inbox Zero (reviewer: Claude Sonnet 5.5)

Source tags: `audit` = rac-audit.md, `product` = inboxzero-product.md, `arch` = inboxzero-architecture.md, `traction` = inboxzero-traction.md. Section numbers refer to each file's own headings. I applied the audit's ERRATA block throughout: Developer ID signing and notarization are configured but have never completed, and the auto-level exfiltration policy finding stands. Statements marked **(inference)** are mine, not the dossiers'.

---

## 1. Verdict in five sentences

1. Inbox Zero is a real, shipping, revenue-claiming business with strong test and CI discipline and a serious structural approach to AI safety, while rac is a technically thoughtful private project that has shipped nothing, has no users, and whose CI never compiles or runs its own tests (audit §0, §5; arch §9, §12).
2. rac's thinking is better than its execution: the agent safety design (TOCTOU re-validation, URL provenance, a critic that never sees page text) is more careful than Inbox Zero's prompt-and-containment approach, but the default `auto` permission level, the lack of any injection evals, and AI-reviewing-AI on security-critical C++ undercut it (audit §3, §5, §7).
3. Inbox Zero's weaknesses (a "source-available" license sold as open source, vague and self-contradicting privacy text, unverifiable SOC 2/CASA claims, a solo founder merging 94% of his own PRs) are trust and honesty problems of a funded SaaS, not existential ones, whereas rac's weaknesses (two Chromium majors behind with a never-run sync, an unproven release path, no business model) are survival problems (product §5.3, §6; traction §1.5, §8; audit §5, §7).
4. The categories differ (an email layer that rents LLM calls vs a Chromium fork that must absorb Google's release cadence forever), so most of Inbox Zero's lessons transfer as process (gated CI, evals, launch discipline, progressive trust defaults) rather than as product, and its growth and monetization playbook mostly does not transfer to a GPL browser with no telemetry.
5. With Arc ending on 2026-12-22, rac should stop adding features and spend the next 30 days proving it can sign, notarize, publish, update, and sync one build, before any launch.

## 3. Where Inbox Zero is clearly better than rac, and why it matters for rac

1. **CI that actually builds and tests the product.** IZ's `test.yml` runs Biome, typechecks, custom checks, sharded unit tests, integration tests against Postgres and Redis, and desktop tests on every push and PR (arch §9). rac's "sanity" job builds for 30 seconds and passes on timeout, and its ~284 tests are never compiled in CI (audit §5). *Matters:* rac's only quality gate is the maintainer's screenshots, and the code it is gating includes 17k lines of agent security logic.
2. **It ships, and ships continuously.** The hosted app deploys on every push to `main`, and the desktop app went 0.1.0 to 0.1.21 between 2026-08-16 and 2026-10-21 (traction §1.4). rac has produced 0 releases, and the release workflow has never succeeded (audit §5). *Matters:* an unshipped signing, notarization, and Sparkle path is the largest unknown on rac's critical path, and the update key and feed URL can never change after the first release (audit §7 risk 1).
3. **A repeatable launch and distribution engine.** Product Hunt #1 twice in three launches, a 167-point Show HN, a 245-URL sitemap with comparison pages, a 25% recurring affiliate program, and a 102K-subscriber YouTube channel (traction §4). rac's site has no download, no waitlist, and 2 unique repo visitors in 14 days (audit §6). *Matters:* Arc's shutdown is a one-time demand spike, and rac has no pipe to catch it. (Caveat: IZ's reach is mostly the founder's pre-existing audience, see §5.)
4. **Structural limits on what the AI can change.** In rules, the LLM only picks which user-written rule matches and fills `{{template}}` placeholders; it cannot add action types or override static recipients, and a 555-line test file guards this (arch §5.3 Layer 2). *Matters:* rac's containment is strong on navigation and input but, at `auto`, lets the model act with the user's logged-in sessions; IZ's design shows how to make "the AI cannot do X" a tested property rather than a prompt (audit §3).
5. **A single, type-enforced LLM choke point.** Every call goes through `createGenerateText` and friends, which require a `promptHardening` level and apply DLP, fallbacks, cost accounting, and redacted logging (arch §5.1, §12). *Matters:* rac's page text, link-hover fetches, critic, and ACP paths are separate flows; uniform enforcement is cheaper than auditing each one by hand (inference).
6. **Evals for model behavior, with semantic judges.** About 431 eval cases across a model matrix, 57 files using LLM judges, and a house rule against keyword assertions (arch §5.5). They run only on `workflow_dispatch` and one injection case mostly tests the sanitizer, but they exist. rac has none: "no red-team suite or eval in the repo" (audit §3). *Matters:* rac's default-`auto` agent decision is currently unfalsifiable.
7. **Progressive-trust defaults for AI.** Rules label, archive, and draft; drafts are not auto-sent; chat sends need a confirmation step; MCP is off until enabled; the docs tell users to "begin with labeling, archiving, or marking messages as read" (product §7.2). rac's default is the most permissive level, `auto`. *Matters:* a browser agent has a larger blast radius than a mail rule (inference), yet is more permissive by default.
8. **Test infrastructure that decouples from the real world.** Emulated Playwright against a fake mail server, local dev with provider emulators and canned AI (arch §9; product §5.2). rac verifies by hand with screenshots. *Matters:* a fake LLM endpoint would let rac regression-test AI surfaces without spending model credits (inference).
9. **Responsiveness to the loudest objection.** HN commenters said "I want a local LM"; the founder promised it, the request was closed, and Ollama/OpenAI-compatible providers plus a DLP redaction mode now exist (traction §5.2). *Matters:* rac already supports Ollama and LM Studio, so it should say so loudly where privacy-minded buyers look (inference).
10. **Operational security hygiene.** An SSRF library with DNS pinning and per-hop revalidation, a 24 h npm release cooldown with install-script allowlist, SHA-pinned read-only Actions, and a `SECURITY.md` with 3-day acknowledgement and 7-day assessment (arch §7; product §6). *Matters:* rac's agent starts npx adapters pinned to exact versions (audit §3) but has no stated disclosure process (inference: the audit does not mention a SECURITY.md).

## 4. Where rac is clearly better than Inbox Zero

Only items that survive scrutiny.

1. **Privacy is architectural, not contractual.** rac has no servers, accounts, telemetry, or site analytics (audit §4). IZ's privacy rests on policy text that contradicts itself and on a vendor stack of PostHog, Sentry, Axiom, Tinybird, Crisp, Loops, and GTM, with a possible prompt-capture path into Sentry spans (product §6; arch §8, S7). A user of rac does not have to trust a company's retention schedule because there is no company data store. *Caveat:* rac still trusts Helium's servers and GitHub for updates.
2. **Agent action gating is more rigorous than IZ's weakest gate.** rac has block/plan/confirm/allow tiers, always-card rules for submit/password/payment/file/risky verbs, TOCTOU element-identity re-validation, URL provenance, containment that survives Stop, and a critic that never sees page content (audit §3). IZ's `manageInbox` (archive, trash, mark read, unsubscribe) runs directly with scope limits "enforced only by prompt", and auto-send rules run with no per-message approval (arch §5.3). *Caveat:* design quality is not behavior, and rac's default level undoes some of it.
3. **License honesty.** rac is GPL-3.0 with credits intact (audit §0). IZ markets "open source under the AGPL" while the LICENSE adds a monetization ban and a 5-user enterprise gate that the self-hosting docs never mention (product §5.3). On this axis rac is simply cleaner.
4. **Documented decisions and admitted limits.** `docs/internals/ai.md` lists seven open concerns itself, including that containment "is not a sandbox", and records constraints and reasons (audit §3, §7 "what is strong"). IZ's docs and marketing disagree on feature maturity, mobile, MCP sending, and compliance wording (product §9).
5. **AI is off by default and never in incognito; the user's own key or local model pays.** (audit §3, §6). IZ's value requires sending mail to LLMs, with AI features behind a paid plan and a card-required trial (product §0, §4). The two are different products, but on "opt-in by default" rac is stronger.
6. **No multi-tenant attack surface.** rac has no shared server holding other people's data, so the class of findings like IZ's global summary cache keyed by raw email text (arch S1) and ownership-cache staleness (S10) cannot occur **(inference)**.

I am deliberately not listing "smaller scope" or "better UI" as rac advantages: the audit shows rac's scope is also sprawling, and no dossier evaluates either product's UI.

## 5. The comparison's traps

1. **Velocity numbers look alike but mean different things.** IZ's 14 commits/day is spread over 3.3 years and 0% AI trailers in Oct 2025 rising to 71% in Oct 2026 (traction §1.6). rac's 96% AI co-authorship covers 23 days (audit §0). IZ's heavily tested foundation was built mostly before heavy agent use **(inference)**, so "IZ proves agent-heavy solo development works" is not shown by the dossiers.
2. **Test counts do not transfer.** 8,700 TypeScript tests that run in minutes (arch §9) are not comparable to a Chromium tree where a build is ~100 GB and a release build is a day or more of runner time (audit §5). Copying "gate every PR on the full suite" literally would be unaffordable; the transferable version is "gate on compile plus the focused unit targets" (inference).
3. **Continuous deployment is not an option for a browser.** IZ deploys on every push; rac's update key and feed URL can never move, and a rushed first release locks in mistakes (audit §7 risk 1). The right rac analogue is small, frequent, tagged desktop releases (the Electron 0.1.x cadence), not web-style CD.
4. **Email is content; a browser is an actor with the user's cookies.** An injected email can mislabel or draft; an injected page can drive a logged-in session. IZ's "safe enough" posture is not evidence for rac's `auto` (inference).
5. **Platform risk is different in kind.** IZ can swap LLM vendors in an env var; rac cannot swap Chromium. IZ's platform dependency is policy (Google OAuth verification, CASA), rac's is code (871 hunks, Glic internals).
6. **Stars, sign-ups, and PH ranks measure a SaaS funnel; rac has deliberately no analytics.** IZ's stars are "a marketing asset more than a contributor funnel" (traction §3.4) and IZ's own trust numbers (25k sign-ups, >$10K MRR) are unverified (traction §8). rac cannot and should not measure itself that way.
7. **The monetization playbook is closed to rac.** IZ's license is built to convert self-hosters into enterprise leads and the CLA enables dual licensing (traction §3.3). A GPL-3.0 fork of GPL code cannot copy this, and the vision rules out accounts and data collection.
8. **Information asymmetry.** The audit of rac had full repo and CI access, while the IZ dossiers are public reads of a shallow clone, with a private marketing repo and private build overlay unseen (arch §11). IZ looks cleaner partly because less of its mess is visible **(inference)**.
9. **Founder distribution is not reproducible.** IZ's founder already had a 102K-subscriber YouTube channel and a prior agency; the dossier itself notes the channel predates the product (traction §2.1, §4.3).

## 7. What rac should not copy

1. **License add-ons that make "open source" untrue** (monetization ban, 5-user gate; product §5.3). rac's GPL-3.0 is an asset and should stay unmodified. Source-available branding on a Helium fork would also conflict with the inherited GPL code.
2. **Badge-ware compliance claims and wording drift**: "SOC 2 certified" with no auditor, CASA with no letter, "Zero Data Retention" over a body that says otherwise (product §6). rac's current disclosure style (a table of what leaves the machine) is better; keep it.
3. **Product analytics, GTM, session replay, and a vendor stack** (arch §8). It contradicts "no data collection" and "never slower"; the audit notes the site has no analytics by design.
4. **Breadth sprawl**: meeting recorder, 19 MCP integrations, Slack/Teams/Telegram bots, SCIM/SSO, a mail client plus assistant (arch §12; product §0 item 8). The audit already shows rac's effort is inverted toward optional features; adding integrations makes the Arc-refugee gap worse.
5. **Prompt-only safety for state-changing actions** (`manageInbox`, `DELETE` rated "low", arch §5.3, §12). rac's design is already stronger; do not regress to prompt text as the barrier.
6. **Default automatic actions that users did not request**, such as "Notify sender" on cold email, which sends mail from the user's account by default (product §7.2, §9.10). The browser equivalent is the `auto` default.
7. **Hidden code overlays and private repos feeding the shipped product** (arch §11). rac's value is reproducibility from patches; the audit's complaint about the `auto` default is a reason to keep everything inspectable, not to add private layers.
8. **Self-merging with bot-only review as the stated process** (traction §1.5: founder PRs 94% merged, median 0.9 h). rac is already there (audit §5); this is a condition to escape, not to copy. IZ's compensating control is its gated CI, which rac lacks.
9. **Founder-brand dependence as the growth model** (traction §4.3). rac has no audience to leverage, and counting on one is not a plan.

## 8. Five changes for the next 30 days (through ~2026-11-24), ranked by impact

Arc shuts down 2026-12-22 (audit §6). The launch window is roughly Dec 1 to Dec 22 and a first release needs a day-plus CI cycle, so these five are about being launchable by ~Nov 25.

1. **Get one signed, notarized release out and prove the update loop.**
   - Run `build.yml` to completion on `main` (the in-flight run is on `ci/sccache-gha-runtime`, audit §5). Per the errata the secrets exist; what is unproven is the path.
   - Verify on a clean Mac: `spctl --assess`, first launch with no Gatekeeper wall, and whether the Keychain "rac Storage Key" prompts again after an update (the audit's inference, with ad-hoc signing no longer expected to apply).
   - Publish a prerelease 0.1.0, then a trivially different 0.1.1, and confirm Sparkle updates between them via `appcast-<arch>.xml`. Do this before any public announcement, because the key and feed URL are permanent (AGENTS.md "Ways to hurt yourself" #6, quoted in audit §7).
   - Flip `RELEASE_READY` only after this passes.
2. **Do the first upstream sync, timeboxed to ~10 days, in a worktree.**
   - Target Helium 0.20.1.1 / Chromium 156 (audit errata). The sync has never been done and `upstream-sync.md` is an untested procedure.
   - Output: the rebased series applying cleanly, a count of conflicting hunks by group (expect `look`, `settings`, `sidebar-reveal`, `spaces`, `pinned`; audit §2), and a written estimate of monthly sync cost.
   - If it blows the budget, ship 0.1.0 as an explicit beta on the older base with a visible security caveat, and say so, rather than silently shipping a browser two majors behind.
   - Run this in parallel with change 1; pipeline proof does not need the final base.
3. **Make the agent safe to ship: default to `ask` or `careful`, add a small injection eval, and label it experimental.**
   - Change the default permission level (a constant and a test in `13-permission-levels`), and add a test that the audit §3 exfiltration chain is blocked at the default.
   - Write 30+ eval cases (hidden text, opacity:0, off-screen text, cross-site-link-then-type) with a semantic judge, run on dispatch. Publish pass rates.
   - If the evals are bad, ship 0.1.0 with the agent off and the chat on. The audit's own ranking (§7 risk 3) calls this the sharpest contradiction with rac's privacy brand.
4. **Put the tests and a compile in CI and turn on branch protection.**
   - Build and run the five unit-test targets on PR or at minimum nightly on `main`; make "sanity" fail on compile errors, not pass on timeout. Delete or fix the Pullfrog workflow that has failed on ~50 runs.
   - Enable branch protection on `main` requiring the lint and sanity checks. Add at least one test each for the largest untested groups (sidebar address bar, onboarding, settings) only if it is cheap; the priority is the gate, not coverage.
5. **Build the minimum Arc-refugee funnel.**
   - A "Moving from Arc" doc and an `/arc-alternative` page on the existing Astro site, a release-count-based success metric (GitHub release download counts, no analytics), and a decision on a minimal Arc import (spaces and pinned/bookmark data) scoped to what can be done in under two weeks. If import cannot be done, say "import is coming" honestly and still launch.
   - Prepare, but do not post, the Show HN and PH launch text for the first week of December, leading with "nothing phones home" and the table of what does leave the machine.

Runner-up (not in the five): a cheap startup and memory benchmark against Helium, to back "never slower than Helium", which currently has no measurement (audit §0, §7 risk 10).

## 9. Where I disagree with the dossiers

1. **audit, body vs ERRATA.** Several body passages still state the old "no Apple Developer account / ad-hoc signing / Gatekeeper wall" conclusions (§1 phase 4, §5 CI state, §6, §7 risk 1). The errata overrides them, but the "Even if it passes, it signs ad hoc" CI bullet and the Keychain-per-update inference should be considered void until the signing path is actually exercised. Anyone reading only the body gets the wrong risk ranking.
2. **audit §6 and §7: "zero measured demand (2 unique visitors in 14 days)" is overstated as evidence.** The repo is deliberately unannounced, the download page is hidden, and rac has no analytics by design. Those numbers measure that nothing has been promoted, not that nobody wants it. The strongest true statement is that demand is untested.
3. **audit §7 risk 6: "hostile-by-policy upstream" overreaches.** The dossier shows Helium bans AI-written contributions, which prevents upstreaming; it does not show hostility toward downstream forks. The real consequence is no help and no goodwill to spend, plus the dependency on Helium's servers for extensions, filter lists, and bangs (audit §4). That is a risk, but it is not evidence of antagonism.
4. **audit §7 risk 7: the effort-inversion framing under-weights agent economics.** 57% of lines are AI and agent, but they were produced by parallel agents (audit §5). The maintainer's attention cost per line was lower than a human-written equivalent, so "spent its runway on the wrong feature" is likely partly true and partly an artifact of line counts **(inference)**. The sharper point is that the release blockers are not agent-parallelizable because they need runner time, secrets, and judgment.
5. **audit §3 exfiltration chain: severity is stated well but the precondition is under-stated.** It needs a hostile page the user has attached or navigated to, plus a run at `auto`. Frontier models may resist; the audit admits this is unmeasured. I agree the policy is wrong to permit it, but "single biggest exposure" is a ranking that depends on an eval nobody has run. The ranking is defensible only because the cost of fixing (a default change) is so low.
6. **product §9 item 4 vs arch §6 on MCP sending.** The product dossier says the docs' tool list "shows only `create_draft`" and marketing says MCP "can never send". The architecture dossier read the code and found a `send_mail` tool that "really sends" behind an `mcp:send` scope, with open dynamic client registration and consent that shows a self-chosen client name (S3). I would treat the marketing claim as misleading, not merely "possibly false".
7. **arch §12 "very low" type-escape counts are overweighted as a quality signal.** The same section says root `tsc --noEmit` is unsupported due to "repo-wide debt", the target is ES2017, and `strictNullChecks` is restated. Counts of `as any` in a repo that cannot run a global typecheck are weaker evidence than they look.
8. **arch §12 and §9: test/source ratio 0.92 as evidence of discipline.** With 73% of recent commits AI-co-authored and 15 skips, a high test count may partly reflect generated tests of uneven value **(inference)**. The meaningful evidence in the dossier is that the tests gate PRs, not that there are many.
9. **traction §2.4 revenue and §8.** The dossier already discounts the $330K figures well.
