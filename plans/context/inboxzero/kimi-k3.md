# Council review: rac vs Inbox Zero (kimi-k3)

## 1. Verdict in five sentences

Inbox Zero is a real product with paying customers, 8,700 tests that actually run in CI, LLM evals, and three years of launch-driven distribution; rac is a 23-day-old, zero-release personal project whose release pipeline has never once completed end to end (rac-audit.md §0, §5; inboxzero-architecture.md §0, §9; inboxzero-traction.md §0). On raw engineering substance per day of effort rac is not embarrassing — its agent safety design (TOCTOU re-validation, containment that survives Stop, a critic that never sees page text) is more thoughtful than most shipping products — but the thinking is good and everything around the code (shipping, syncing, testing, review, users) is missing (rac-audit.md §7, "What is genuinely strong"). rac's privacy posture and license honesty are genuinely better than Inbox Zero's: rac phones home to nobody and is plain GPL-3.0, while Inbox Zero sends email content to cloud LLMs, stores derived content in plaintext, and markets AGPL-plus-restrictions as "open source" (rac-audit.md §4; inboxzero-product.md §5.3; inboxzero-architecture.md §3). The single most damning rac fact is not the missing release but the inverted priorities: 57% of its new code is AI/agent work that its own roadmap calls optional phase-5, while Arc import — the one feature that could capture the Arc shutdown window on 2026-12-22 — does not exist (rac-audit.md §1, §7.7). If rac copies Inbox Zero's process discipline (CI-gated tests, eval suites, structural containment of AI output, a launch playbook) and refuses its license games and feature sprawl, it can be a credible niche browser; if it keeps its current trajectory it will be a well-documented private build that misses its only market window.

## 3. Where Inbox Zero is clearly better than rac, and why it matters for rac

1. **Tests that run.** Inbox Zero has ~8,700 test cases in 1,302 files, and `test.yml` runs lint, typechecks, sharded unit tests, integration tests against Postgres/Redis, and desktop tests on every push and PR (inboxzero-architecture.md §9). rac has ~284 cases that CI never compiles or runs, and its "sanity" build passes on a 30-second timeout (rac-audit.md §5). Why it matters: rac is 110k patch lines of security-sensitive C++ maintained by one person; without CI gating, every upstream sync will silently break things.
2. **LLM evals, including security evals.** Inbox Zero has ~430 eval cases across a model matrix with semantic judges, including `prompt-security-core-paths.test.ts` and phishing-hardening evals (inboxzero-architecture.md §5.5). rac ships a browser agent whose default policy permits an injection-driven exfiltration chain and has "no red-team suite or eval in the repo" (rac-audit.md §3). For a privacy-first browser this is the sharpest gap between the two projects.
3. **A single LLM choke point with mandatory hygiene.** Every Inbox Zero model call passes through one module that requires a `promptHardening` declaration, applies DLP policy, fallback chains, cost accounting, and redacted logging (inboxzero-architecture.md §5.1). rac's injection defense is a nonce-wrapped prompt that "depends on the model obeying" and its email-content analog (page text) is capped but not escaped (rac-audit.md §3). A choke point is how one person keeps AI behavior auditable at scale.
4. **Structural containment of AI output.** In Inbox Zero's rule engine the LLM can only pick which rule matches and fill user-written `{{template}}` placeholders; it cannot add action types or override static recipients, enforced by a 555-line dedicated security test (inboxzero-architecture.md §5.3, Layer 2). rac's agent instead classifies free-form actions and gates them by policy, which is inherently leakier — the auto-level chain proves it (rac-audit.md §3). Constraining the output space beats classifying the output stream.
5. **Shipping as a habit.** Inbox Zero deploys on every push to main, cuts desktop releases about twice a week during bursts, and has executed three Product Hunt launches with two #1-of-day results (inboxzero-traction.md §1.4, §4.1). rac's release workflow has never succeeded and its download page is hidden behind `RELEASE_READY = false` (rac-audit.md §5, §1). Why it matters: with Arc shutting down 2026-12-22, distribution muscle is the scarce asset, not features.
6. **An audience and a capture funnel.** Inbox Zero has 12.8k stars, ~245 sitemap URLs of SEO content, comparison pages against every competitor, a YouTube channel, and a trial funnel (inboxzero-traction.md §4.4; inboxzero-product.md §1). rac has 2 unique repo visitors in 14 days, no waitlist, and no analytics by design (rac-audit.md §6). rac doesn't need Inbox Zero's volume, but it needs *some* capture mechanism before the Arc window, or even a perfect launch lands in a void.
7. **External contribution handling.** Inbox Zero merges 66% of external human PRs with a 34.6-hour median and has ~20 people with 10+ commits (inboxzero-traction.md §1.5, §1.2). rac has zero external contributors and no path for one to succeed (no working CI build a contributor could verify against) (rac-audit.md §5). For a GPL browser fork, outside contributors are the only plausible escape from bus-factor-1.
8. **Cost and usage accounting.** Inbox Zero tracks per-call token cost against a generated pricing table and has weekly spend-limit scaffolding (inboxzero-architecture.md §5.4). rac has no usage visibility at all; a user running its agent against a paid API has no idea what a browsing session costs (rac-audit.md §3). Inference: BYO-key users will blame the browser, not the provider, for surprise bills.

## 4. Where rac is clearly better than Inbox Zero

1. **Privacy architecture is structurally better, not just better-worded.** rac has no servers, no accounts, no telemetry, and AI is off by default with incognito excluded; page content only leaves the machine to a provider the user chose, and Ollama/LM Studio local models are a first-class in-product option (rac-audit.md §3, §4). Inbox Zero stores AI-drafted replies, digest summaries, chat transcripts, attachment text, and meeting transcripts in plaintext Postgres, sends email content to up to 20 subprocessors, and its privacy policy contradicts itself on retention ("Zero Data Retention" next to "not stored beyond what is required for abuse and misuse monitoring") (inboxzero-architecture.md §3; inboxzero-product.md §0.6). Inbox Zero's local-model support exists only via self-hosting, which its own docs show is a heavy lift (inboxzero-product.md §5.2).
2. **License honesty.** rac is plain GPL-3.0 inherited from Helium, with no additional terms (rac-audit.md §0). Inbox Zero's LICENSE prepends a commercial-monetization ban and a 5-user enterprise-license requirement to AGPL, GitHub classifies it as NOASSERTION, and the marketing site still says "open source under the AGPL" without mentioning the restrictions anywhere in the self-hosting docs (inboxzero-product.md §5.3, §9.1). This is the one area where rac should feel no inferiority at all.
3. **The always-a-card invariant for irreversible UI actions.** At every permission level including `auto`, rac's ActionGuard forces a confirmation card for submit controls, Enter, password/payment/file fields, and risky verbs (buy, send, delete, sign in, upload) (rac-audit.md §3). Inbox Zero rates DELETE, MARK_SPAM, and ARCHIVE as "low" risk, and once a REPLY/SEND/FORWARD rule exists it runs with no per-message approval (inboxzero-architecture.md §5.3, Layer 3). rac's auto level has its own hole (cross-origin navigate and typing), but the submits-and-payments-always-confirm line is one Inbox Zero does not draw.
4. **No dark patterns and no monetization pressure on design.** rac has no card-required trial, no plan gating, no cookie-consent machinery, no analytics on its site at all (rac-audit.md §4, §6). Inbox Zero requires a credit card for its 7-day trial, gates the AI that is the product's entire point behind $20/mo, runs GTM and PostHog on the homepage, and defaults the Cold Email rule to *emailing the sender* — an automatic outbound message that contradicts its own "drafts, not sends" framing (inboxzero-product.md §0.2–0.3, §6, §7.2).
5. **Honest internals documentation.** rac's `docs/internals/ai.md` lists its own open concerns, including ones unflattering to the product (rac-audit.md §3, "What is genuinely strong"). Inbox Zero's public claims repeatedly outrun its evidence: "SOC 2 certified" wording its own blog admits is wrong, a trust center with 0 documents, Reply Zero marketed as a headline feature while docs call it Early Access (inboxzero-product.md §0.5, §9.3, §9.7).

(That is the honest list. Claims that rac's agent is "safer overall" or its engineering is "cleaner" do not hold up against the auto-level exfiltration chain and the never-run test suite, so they are excluded.)

## 5. The comparison's traps

1. **SaaS economics don't transfer.** Inbox Zero's $20–50/seat/month funds its CI, eval runs, and 191 dependencies (inboxzero-product.md §5.1; inboxzero-architecture.md §0). rac has no revenue model and GPL-3.0 plus BYO-key AI leaves no margin to capture (rac-audit.md §6). Copying Inbox Zero's operating cadence without its cash flow is a recipe for burnout, not growth.
2. **"Ship on every push" means something different for a Chromium fork.** Inbox Zero's continuous deployment is a Vercel push-to-main (inboxzero-traction.md §1.4). rac's release is a multi-hour, ten-phase signed-and-notarized binary build that has never completed once (rac-audit.md §5). rac should copy the *discipline* of frequent releases, not the *mechanism*; a weekly cadence is the realistic ceiling.
3. **Feature breadth is a winning strategy for Inbox Zero and a losing one for rac.** Inbox Zero's sprawl (notetaker, Slack bots, CRM integrations) rides on a conventional Next.js app where each feature is incremental (inboxzero-architecture.md §12). Every rac feature is permanent rebase debt across 871 upstream hunks, 320 of them in the most volatile part of Chromium (rac-audit.md §2, §5). The same "just add it" instinct that grew Inbox Zero will kill rac at the next Chromium major.
4. **Stars and launches are a lagging indicator for a browser.** Inbox Zero's 12.8k stars are a launch-driven marketing asset, with 45 watchers and a thin contributor base (inboxzero-traction.md §1.1, §8.1). A desktop browser's adoption gate is trust (signing, updates, security posture), not launch-day upvotes; rac chasing PH-style launches before its release pipeline works would invert cause and effect.
5. **The risk profiles of "AI agent" differ categorically.** Inbox Zero's worst injection outcome is a mislabeled or wrongly auto-archived email, or a bad auto-reply (inboxzero-architecture.md §5.3, residual risk). rac's agent acts inside the user's logged-in browser profile, where a cross-origin read plus typed exfiltration can leak live session data (rac-audit.md §3). Inbox Zero's "prompt text plus containment" posture is calibrated to a lower-stakes domain; importing its comfort level into a browser agent would understate the threat.
6. **Compliance theater is a SaaS enterprise-sales tool.** Inbox Zero's SOC 2/CASA claims exist to unblock enterprise deals (inboxzero-product.md §6). rac has no enterprise motion and no way to buy equivalent trust; its trust must come from reproducible builds, signed releases, and the privacy architecture it already has. Spending a dollar or a day on badges would be wasted.

## 6. What rac should steal, ranked

1. **CI that actually compiles and runs the tests, gating every PR.** Inbox Zero runs its full suite on push and PR (inboxzero-architecture.md §9). Cost to rac: real money and time — Chromium CI is expensive, and the existing five test targets must first be wired into a build. Worth it because it is the precondition for everything else: upstream syncs, external contributors, and the 284 existing tests becoming real instead of decorative (rac-audit.md §5).
2. **A prompt-injection red-team eval suite, modeled on Inbox Zero's eval matrix.** Inbox Zero runs ~430 evals across models with semantic judges, including security evals (inboxzero-architecture.md §5.5). Cost: days of work plus ongoing API spend, and the discipline of running it on `workflow_dispatch` at minimum. Worth it because rac's single biggest security exposure — the auto-level exfiltration chain — is currently unmeasured, and "whether real models follow such an injection is an empirical question nobody has measured" (rac-audit.md §3).
3. **Structural containment of model output.** Inbox Zero's rule engine lets the LLM fill only user-written template placeholders and nothing else, with a 555-line security test proving it (inboxzero-architecture.md §5.3). rac's equivalent: constrain agent action arguments (URLs, typed text) to values grounded in user messages or validated snapshots, enforced in the action runner rather than classified after the fact. Cost: a redesign of the tool-call layer it already has. Worth it because classification-based gating is exactly where the auto-level hole lives (rac-audit.md §3).
4. **A single LLM choke point with a mandatory per-call-site hardening declaration.** Inbox Zero requires every call to declare `promptHardening` and applies DLP, escaping, and logging uniformly (inboxzero-architecture.md §5.1–5.2). rac should add HTML/format escaping of page text (its nonce wrapper is purely model-dependent) and route all provider calls through one auditable module. Cost: a refactor of the direct-provider loop. Worth it because rac currently has no equivalent checklist of which call sites send page content where (rac-audit.md §3).
5. **AGENTS.md engineering norms with teeth.** Inbox Zero's AGENTS.md bans keyword assertions in evals, mandates semantic judges, requires the provider abstraction, and sets PII logging rules (inboxzero-architecture.md §12). rac's AGENTS.md is strong on process warnings but its verification policy is "agent takes screenshots" (rac-audit.md §5). Cost: an afternoon of writing. Worth it because with 96% AI-authored commits, the written norms are the actual engineering manager (rac-audit.md §0).
6. **The launch playbook: comparison pages and a capture mechanism for Arc refugees.** Inbox Zero's durable growth lever is programmatic SEO — a comparison page for every competitor and vertical landing pages (inboxzero-traction.md §4.4). rac's analog is cheap and obvious: an "Arc is shutting down — import to rac" page, plus a waitlist or newsletter (which requires relaxing the no-data-collection stance by one email field). Cost: marketing time and a small privacy-policy compromise. Worth it because the Arc window closes 2026-12-22 and rac currently has zero audience capture (rac-audit.md §6).
7. **Per-call cost and usage visibility for BYO-key users.** Inbox Zero tracks token cost per call against a pricing table (inboxzero-architecture.md §5.4). Cost: modest — a running tally in the chat/agent UI. Worth it because rac's agent makes autonomous multi-step calls (25-step cap) against the user's own paid key, and surprise bills would poison the exact power users rac needs (rac-audit.md §3). (Inference about user reaction; the capability gap is factual.)
8. **Squash-merge-everything PR discipline.** Inbox Zero has zero merge commits in its recent history; everything lands as a reviewed, squash-merged PR (inboxzero-architecture.md §12). rac lands 70% of commits directly on unprotected main (rac-audit.md §0). Cost: slower iteration for one person, plus turning on branch protection (free). Worth it because rac's review is currently "AI reviewing AI" with zero approvals ever, and a patch stack this order-dependent needs a checkpoint per change (rac-audit.md §5, §2).
9. **Dogfood-the-setup friction test.** Inbox Zero invested in `npx @inbox-zero/cli setup` after self-host sign-in issues became its top complaint class (inboxzero-traction.md §5.2, §1.5). rac's analog: script and time a clean-machine install from DMG to working update. Cost: one sacrificial Mac or VM per release. Worth it because rac's first-run experience (Gatekeeper, onboarding, update feed) has never been exercised by anyone, including its own CI (rac-audit.md §5, ERRATA).

## 7. What rac should not copy

1. **AGPL-plus-extra-terms license games.** Inbox Zero's "open source" marketing over a license GitHub reports as NOASSERTION, with a 5-user enterprise gate that its own self-hosting docs never mention, is its single most criticized trust issue (inboxzero-product.md §5.3, §9.1; inboxzero-traction.md §3.3). rac's plain GPL-3.0 is an asset; any additional-terms temptation would cost more trust than it could ever earn revenue.
2. **Feature sprawl.** Inbox Zero carries a meeting recorder, Slack/Teams/Telegram bots, CRM integrations, and SCIM in one 628k-line Next.js app, with the type debt to show for it (inboxzero-architecture.md §0, §12). rac's equivalent sprawl compounds as rebase debt across 217 upstream files (rac-audit.md §2). The correct rac instinct is the opposite of Inbox Zero's: subtract.
3. **Self-reported compliance claims.** "SOC 2 Type 2 certified" with a trust center showing 0 documents, wording the company's own blog admits is wrong (inboxzero-product.md §0.5, §9.7). rac's credibility rests on claims matching code; it already has two unbacked claims of its own to fix ("Never slower than Helium," "thin layer") and should not add a third genre (rac-audit.md §7.10).
4. **Cloud-first AI with derived-content retention.** Inbox Zero stores summaries, drafts, chat transcripts, and meeting transcripts in plaintext server-side and sends content to up to 20 subprocessors (inboxzero-architecture.md §3; inboxzero-product.md §6). This is the exact posture rac exists to oppose; its differentiator is that nothing leaves the machine except to the user's chosen provider (rac-audit.md §4).
5. **Default-outbound actions.** Inbox Zero's default Cold Email rule emails the sender automatically — an outbound message from the user's account that its "drafts, not sends" framing obscures (inboxzero-product.md §0.3, §7.2). rac's always-a-card invariant for sends is better; keep it, and extend it rather than relax it.
6. **Card-required trials and plan gating.** A 7-day trial requiring a credit card, with the actual product behind $20/mo (inboxzero-product.md §0.2). rac has no business infrastructure for this and no need; copying SaaS monetization mechanics onto a GPL browser with zero users would be cargo cult.

## 8. The five changes rac should make in the next 30 days

Ranked by impact, against the 2026-12-22 Arc shutdown (58 days out per rac-audit.md §6).

1. **Ship release 0.1.0 through the real pipeline, then update to 0.1.1.** Get `build.yml` green on `main` with Developer ID signing and notarization (the secrets exist per ERRATA; the path has simply never completed), publish a DMG, and then publish a second release purely to prove the Sparkle feed updates the first one (rac-audit.md §7.1; ERRATA). Nothing else matters if the download is a Gatekeeper wall. Specific exit criteria: a clean-machine install with no `codesign --sign -` fallback, and a verified automatic update.
2. **Build Arc import.** Spaces, pinned tabs, favorites, and settings import from Arc is the one feature that converts an Arc refugee this quarter; it is currently phase-5 and nonexistent while the phase-5 agent holds ~17k lines (rac-audit.md §1, §7.7). Pair it with an "Arc is shutting down" landing page (steal #6 above). Scope it to the smallest useful import and ship it in 0.1.x, not 0.2.
3. **Sync to Helium 0.20.1.1 / Chromium 156 now, and put the sync on a calendar.** rac is two Chromium majors behind with known public security bugs, has never performed a sync, and every week of feature work makes the first one bigger (rac-audit.md §5, §7.2; ERRATA). Do it while the stack is 23 days old, not 90. This will hurt; that is the point of doing it now.
4. **Flip the agent default from `auto` to `careful`, and gate the two free primitives.** Cross-origin navigation and typing model-generated text into the attached site should not be `kAllow` at the default level, per the audit's exfiltration chain (rac-audit.md §3; ERRATA). Add a minimal injection eval set (steal #2) in the same change so the policy is measured, not just asserted. Cost to UX is real but survivable; a publicized exfiltration demo against a privacy-first browser is not.
5. **Turn on CI tests and branch protection together.** Wire the five existing test targets into CI (even a subset that runs on the 30-second sanity job's successor), require the check for merge, protect `main`, and route the 70% direct pushes through PRs (rac-audit.md §0, §5). This is deliberately last of the five only because items 1–4 are deadline-bound; if it slips, items 1–4 will silently regress.

## 9. Where I disagree with the dossiers

1. **rac-audit §7 ranking puts "ships nothing" at #1; I would put the upstream sync gap there.** (My judgment, not a factual dispute.) A broken release pipeline is recoverable in a concentrated week now that signing secrets exist (ERRATA). A Chromium fork that falls permanently behind majors is what structurally kills forks, as the audit itself says in the very next line (rac-audit.md §7.2). Shipping is the loudest risk; the sync is the lethal one.
2. **Inbox Zero architecture's "no IDOR found" (§7, sampled 12 queries) is thin evidence for a strong claim.** Twelve sampled queries in a 291-route, 217-server-action app cannot support "tenant isolation is consistent" as more than a preliminary signal; the dossier's own confidence markers ([R] from a sub-reader) make this a place where the architecture review overstates its reach. Not a claim of a bug — a claim about confidence.
3. **Inbox Zero's "drafts, not sends" default framing survives both dossiers too easily.** The product dossier flags that the default Cold Email rule emails the sender (inboxzero-product.md §0.3, §7.2), and the architecture dossier confirms auto-send rules run without per-message approval once enabled (inboxzero-architecture.md §5.3). I think the correct summary is harsher than either dossier's: Inbox Zero's default posture includes automatic outbound mail, and its headline safety claim should be discounted accordingly.
4. **The rac audit underweights the agent as a strategic choice, even while correctly flagging the sequencing.** Risk #7 calls the agent "the feature least likely to make an Arc refugee switch" (rac-audit.md §7.7), which is true for acquisition — but the agent is also rac's only durable differentiation against Ardia and Yab, the competitors the audit itself names (rac-audit.md §6). The failure is not that the agent exists; it is that it exists at `auto` with no evals and no release behind it. (Inference/strategic judgment.)
5. **The Inbox Zero traction dossier's star-history trend (~300/month) is presented with appropriate low confidence, but I'd go further: it should not be used at all.** The snapshots ("late 2025", undated StackShare) are too loosely dated to support a rate (inboxzero-traction.md §1.7), and the dossier's own §8.1 argues stars measure launch awareness rather than engagement, which makes a growth-rate derivative doubly meaningless.
6. **Both products' dossiers treat AI co-author trailers as a lower bound on AI authorship, which is right, but neither considers the reverse distortion.** Inbox Zero's trailers jumped from 0% (Oct 2025) to 71% (Oct 2026) of commits (inboxzero-traction.md §1.6); some of that rise is surely adoption of trailer-writing convention rather than adoption of AI. The 73% figure for Inbox Zero and 96% for rac are probably not comparable to each other as "how much AI wrote this," only as "how much AI was credited." (Inference.)
7. **Missing context in the Inbox Zero dossiers: the platform-threat asymmetry.** The traction dossier notes Google's own AI inbox features as a platform threat only in passing, via a founder HN comment (inboxzero-traction.md §6). For a product whose entire value is a layer on Gmail/Outlook, the platform owner shipping the same features native is an existential risk of the same class as rac's Chromium-rebase risk — and it receives a fraction of the analysis that rac's upstream risk receives. If the council weighs rac's platform risk at #2, consistency demands Inbox Zero's Gmail-dependency risk be scored lower than the 7 I gave it, or the dossiers should have pushed harder on it. I left my score at 7 only because Microsoft Graph provides partial diversification.
